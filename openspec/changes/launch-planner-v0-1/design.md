# Planner 0.1.0 design

## Context

Planner has an initialized OpenSpec project and no application code. The comparison and import baselines are PLANKA Community 2.3.0 at `ce6d499ae16202a727d7dbb9238b48422ab60da9` and 2.3.1 at `27219fd3635e695b2ec4e2a9d9ed6bec6560370f`. The source server uses Sails, Knex and PostgreSQL. The client uses React, Redux and Socket.IO. PLANKA 2.3.1 fixed editing on boards where a member has no username, so null usernames belong in the acceptance fixtures. The two patch releases share a database schema. [PLANKA 2.3.0](https://github.com/plankanban/planka/releases/tag/v2.3.0) · [PLANKA 2.3.1](https://github.com/plankanban/planka/releases/tag/v2.3.1) · [Server dependencies](https://github.com/plankanban/planka/blob/v2.3.1/server/package.json) · [Client dependencies](https://github.com/plankanban/planka/blob/v2.3.1/client/package.json) · [Release comparison](https://github.com/plankanban/planka/compare/v2.3.0...v2.3.1)

The Architect traced tagged controllers, helpers, models and frontend workflows and checked aggregate facts against the isolated 2.3.1 restore. The implementation uses four companion contracts. Follow [platform.md](platform.md) for the repository, storage and native install, [workspace.md](workspace.md) for routes and transitions, [access-and-mcp.md](access-and-mcp.md) for permissions and client behavior, and [migration.md](migration.md) for source mappings and exception handling. [tasks.md](tasks.md) pins the dependency order and evidence for each handoff.

## Goals / Non-Goals

- Deliver a working kanban application that teams can adopt with existing work, with one permission model for the browser and MCP.
- Make a single-host install reproducible and recoverable. Give the operator a chance to verify the migrated result before users start editing it.
- Release support covers native Ubuntu 24.04 LTS x86-64 on systemd, local Planner accounts and the Community workflows specified here. Additional OS packages, container packaging, high availability, bidirectional sync, drop-in PLANKA API compatibility and independently designed equivalents of paid-only features are outside 0.1.0.

## Decisions

### 1. Independent application with a PLANKA compatibility baseline

Build Planner from a clean repository. Use upstream releases, schema, documentation and observed Community behavior to specify compatibility. The v2.3.1 distribution distinguishes Community and Pro/Enterprise source and has terms governing use, distribution and preservation of notices. A wholesale fork would also leave the team rewriting the SQL persistence, changing authentication and replacing paid-edition integration points throughout the application. An independent build gives Planner control of those contracts and its product identity. [Tagged upstream license](https://github.com/plankanban/planka/blob/v2.3.1/LICENSE.md) · [Community terms](https://github.com/plankanban/planka/blob/v2.3.1/LICENSES/PLANKA%20Community%20License%20EN.md) · [Commercial terms](https://github.com/plankanban/planka/blob/v2.3.1/LICENSES/PLANKA%20Commercial%20License%20EN.md)

Create a release coverage matrix keyed by observed workflow or source entity. Use the rows below as the initial baseline. Each row must end in a Planner acceptance case, a supported import mapping, or an explicit release exclusion with its effect. Bring any later-discovered Community gap to the owner before changing scope. Use independent UI assets, copy and components. The initial interaction design uses a project sidebar, board tab strip, a board command bar and a card inspector with focused sections for details, checklist and activity. Review those screens for a distinct composition, hierarchy and visual treatment.

| Area | Planner 0.1.0 coverage |
| --- | --- |
| Workspaces | Private and shared projects, independent hidden state, managers and favorites, boards, board membership, editor and viewer access, comments where permitted. Shared projects still require access checks. |
| Board operation | Kanban, grid and list views. Create and edit finite lists and cards, duplicate cards, reorder and move, sort finite lists, bulk archive from closed lists, restore, clear trash after confirmation, and filter active work. Preserve saved filter recall, board clipboard actions and description draft recovery. |
| Card details | Rich description, labels, members, project and story types, due dates and completion, stopwatch, task lists, ordered tasks and linked cards, custom fields, file and URL attachments, comments. |
| Collaboration | Activity history, in-app notifications, board and card subscriptions, and live board updates. |
| Administration | Local accounts, provisioning and disabling, password reset, MFA enrollment and recovery codes, trusted devices, personal settings, connected MCP clients, and permission and actor audit. |
| Import-only or deferred | In-app notifications are included. PLANKA API keys, outgoing webhooks, SMTP, external notification delivery, Trello board import and permanent account deletion are outside 0.1.0. Legacy browser-local preferences remain outside the import. Preserve allowlisted integration metadata in the report, omit secrets and retain the original snapshot. |

### 2. Node.js modular monolith and React client

Use Node.js 24 LTS and TypeScript. Build the browser client with React and Vite as static assets served by Fastify. Use the official MongoDB Node.js driver. Use a single application process with REST, account and consent routes, an authenticated event stream for boards, and the MCP adapter. Share request schemas and a framework-independent application layer for actor resolution, authorization, domain mutations and audit. Use PostgreSQL's Node driver only in migration tooling.

Fastify gives the application request validation, scoped plugins and an official MCP SDK integration. Express is workable with more assembly for validation and application structure. NestJS adds a framework layer that a single-process release can defer. React fits an interactive board and accessible drag-and-drop. A server-rendered React framework would add a second server abstraction for a sign-in-gated application. [Node.js LTS schedule](https://nodejs.org/en/about/previous-releases) · [MCP Fastify integration](https://ts.sdk.modelcontextprotocol.io/v2/serving/fastify.html) · [MongoDB driver support matrix](https://www.mongodb.com/docs/drivers/compatibility/?all-languages=nodejs&interface=driver)

Use distinct collections for users, projects, boards, lists, cards, relationships, and activity and notification records. Keep card identities independent of position and use server-generated ranks, a stable ID tie-break and a revision precondition on conflicting writes. The web client can optimistically render moves and refetch when revisions conflict or the event sequence has a gap. Use board, list and membership indexes for load and authorization, and unique keys for relationships and migration identifiers. Store attachment bytes in a private content-addressed file store and authorize every download through the associated record. Stage and verify file bytes before committing references. Garbage-collect unreferenced content after a grace period.

Use one application writer. Confirm exclusive ownership across the service and maintenance tools. Single-document changes use revision checks and atomic conditional updates. Each multi-document command has a durable unique journal entry and deterministic, replayable updates covering domain data, file references and the event record. Route web, MCP, event and background work through the same commit boundary. Keep readers behind a shared gate until the command finishes. Publish authorized events only after commit with stable IDs for deduplication. Reconcile pending work before reporting readiness on startup. Keep the service in maintenance if recovery cannot safely complete. Stage slow upload bytes before taking the write gate. Document single-host write throughput and exercise interruption at journal, record, file and notification boundaries before release.

### 3. Native package with private MongoDB

Ship a signed release manifest with a `.deb` and exact checksums. Bundle a pinned MongoDB 8.0 Community Server and a pinned Node.js runtime under `/opt/planner`. Use separate `planner` and `planner-mongodb` systemd services and OS users, with service configuration in `/etc/planner` and isolated state under `/var/lib/planner`. Use loopback `127.0.0.1:27431` by default, configurable during install. Require MongoDB authorization and an app credential limited to the Planner database. Bind the app privately behind an operator-configured TLS reverse proxy for HTTPS. Ensure forwarded headers are accepted only from the configured proxy.

Run one authenticated standalone `mongod`. This is a single failure domain and uses the application journal for changes spanning multiple documents. A replica set would add lifecycle and network configuration. Use authenticated bootstrap, an installation identity marker, dedicated data and log paths, and an explicit port-conflict check. Never adopt a listening MongoDB or change a host-managed service. Publish the exact bundled MongoDB corresponding source, applicable notices and offer or access terms alongside binaries as required by the release distribution method, with a manifest linking each binary to its source. Verify this release requirement before distributing the installer. [MongoDB Ubuntu support](https://www.mongodb.com/docs/v8.0/tutorial/install-mongodb-on-ubuntu/) · [MongoDB production transaction requirements](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/) · [MongoDB SSPL](https://www.mongodb.com/legal/licensing/server-side-public-license)

### 4. Import from a consistent, read-only snapshot

Use an operator-provided PLANKA PostgreSQL backup restored in a disposable, isolated staging environment and a matching copied asset directory. Accept a restored PostgreSQL connection with a least-privilege read-only user and an explicit release and edition manifest. Support local file snapshots and object-backed installations through a matching read-only object snapshot or a materialized copy. Keep either layout independent of production storage credentials. The normal installer does not execute dump SQL. Document preparation for upstream's full-cluster dump workflow in the isolated restore environment. Pin supported readers and reject unknown schema differences. [Tagged migration history](https://github.com/plankanban/planka/tree/v2.3.1/server/db/migrations) · [Tagged models](https://github.com/plankanban/planka/tree/v2.3.1/server/api/models) · [PLANKA backup example](https://github.com/plankanban/planka/blob/v2.3.1/docker-backup.sh) · [PostgreSQL restore behavior](https://www.postgresql.org/docs/16/app-pg-dumpall.html)

| Source data | Target handling |
| --- | --- |
| Users and access | Preserve source ID, nullable username, display data, disabled status, explicit roles, project managers, board editor or viewer roles, private or shared type, independent hidden state and viewer comment permission. Keep the global project-owner creation role separate from individual project management. Admins can read unowned shared boards. Owner-managed private boards require an explicit relationship. Shared membership follows source rules and does not grant anonymous or unrelated-user access. Block cutover for an unmapped role or access relationship. |
| Projects, boards, lists and cards | Preserve parent relationships and deterministic order by source position and ID, active, closed, archived and trash states, previous placement where supported, card types, due dates and completion, descriptions, labels, assignees and supported settings. |
| Nested content | Resolve task list, task, linked card, custom field definition, group and value references after identity mapping. Distinguish references from free text and preserve nulls and typed values. |
| History and follow state | Preserve supported comments, actors, timestamps, activity and notification history, read flags, favorites and subscriptions. Keep historical references resolvable or label them as deleted. |
| Media | Verify file attachments, avatars, card covers and project backgrounds by expected path, byte size and digest. Preserve URL attachments as inert links with supported schemes. Copy only expected files. |
| Site configuration and credentials | Allowlist harmless settings with known semantics. Report browser-local preferences, including saved filters, as outside the database snapshot. Exclude password hashes, sessions, API keys, trusted devices, TOTP and recovery secrets, SMTP credentials and secret-bearing webhook values. Retain safe metadata for the operator report. Imported users complete a verified Planner reset and users with source MFA re-enroll before receiving ordinary sessions or integration grants. |

Process a source snapshot in bounded batches. Preserve upstream bigint IDs as exact decimal strings and maintain a unique mapping per generation, entity type and ID. Normalize timestamps to UTC and retain source microseconds in provenance. Classify broken active relationships, unavailable assets, stale prior lists, historical snapshots and orphan notifications separately. Retrying an interrupted import must verify the snapshot fingerprint and reuse the same mapping and file digests. A different snapshot requires a new generation. Activate the approved stage read-only with one pointer update and enable writes only after verification. [Tagged private-board access](https://github.com/plankanban/planka/blob/v2.3.1/server/api/controllers/boards/show.js) · [Tagged asset layout](https://github.com/plankanban/planka/blob/v2.3.1/server/config/custom.js)

For a cold migration, use a privileged local installer command to bind a short-lived, one-time setup grant to a named, enabled imported administrator in the staged generation. The operator verifies the recipient before transferring the grant. The administrator completes recovery and, if required, factor enrollment through a route limited to enrollment while staging is closed. This establishes a usable account for cutover and subsequent account recovery without changing source roles. If the source has no eligible administrator, allow the local operator to explicitly create a new Planner administrator and audit that decision. Use verified email for login where a source username is absent.

### 5. One account permission model for web and OAuth

Use local accounts with password hashing, secure browser sessions and administrator-issued recovery. Use maintained `oidc-provider` v9 for the OAuth authorization server, with provider state in the private MongoDB service and consent screens tied to authenticated Planner accounts. Keep the public issuer and resource URL stable. Keep browser session identities and MCP client grants distinct. Use a narrow connection to the same account and access policies and issue resource-bound tokens with explicit Planner read and write scopes. Use OAuth protected resource and authorization server metadata, issuer identification, resource indicators and PKCE S256. Return an HTTP 401 discovery challenge on unauthenticated MCP calls and list the canonical issuer first. Use published Client ID Metadata Documents (CIMD) as the default onboarding path for Codex and Claude. Advertise public-client token exchange and verify the provider's pinned CIMD support, restricted metadata fetching, and the pre-registered client option. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [oidc-provider](https://github.com/panva/node-oidc-provider)

Match redirect hosts and paths to the registered URI and allow ephemeral ports only for the clients' documented loopback redirects. Cover Codex's issuer-bound loopback flow, Claude Code's registered `localhost` and `127.0.0.1` callbacks, and the fixed hosted callback `https://claude.ai/api/mcp/auth_callback`. Accept form-encoded token exchanges and refreshes. Exercise real public-client token rotation and the `invalid_grant` response after revocation. [Codex OAuth registration and callbacks](https://learn.chatgpt.com/docs/extend/mcp?surface=cli#oauth-client-registration-and-callbacks) · [Claude OAuth requirements](https://claude.com/docs/connectors/building/authentication)

Use revocable opaque access tokens and validate the issuer, audience, expiry, scope, user and client grant at the protected resource. Refresh tokens rotate and a revoked grant invalidates refresh and active streams. Re-evaluate current board access for reads, writes and data delivery. Treat connected clients as acting for a user, validate inputs before domain calls, and record the actor and client in the audit history. Use the same access test matrix for browser REST, file responses, live updates and MCP. Redact secrets and minimize identifiers in logs and import reports.

### 6. Streamable HTTP MCP

Use the official MCP TypeScript SDK v2 Fastify adapter to expose `/mcp`. Implement 2026-07-28 with `server/discover`, per-request version and capability metadata, and the advertised request and subscription capabilities. Support 2025-11-25 Streamable HTTP clients through the SDK compatibility path with that profile's initialization and version handling. Follow profile-specific rules for POST, streaming, session behavior if used, and errors. Publish a protocol and client support matrix with the release. [Current Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) · [2025-11-25 transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) · [TypeScript SDK v2](https://ts.sdk.modelcontextprotocol.io/v2/)

| Capability | Initial application surface |
| --- | --- |
| Tools | List, search, create and update projects and boards, manage project and board memberships according to role, and create, update and order lists and cards. Cover duplicate, move, archive and restore, finite-list sort and closed-list bulk archive, labels, assignees, dates, custom field definitions and values, checklist groups and tasks, comments, favorites, subscriptions, notification state and attachment metadata and links. Return bounded, typed results and handle mixed permission cases. |
| Resources | Board summaries and card details selected by stable Planner IDs, including permission-checked reads and pagination where relevant. Provide references to authorized Planner attachment downloads. Binary file transfer uses the authenticated web application. |
| Prompts | Board status and triage templates. Inputs name a board and any filters and access stays within the connected user's authorized data. |
| Transport utilities | Protocol errors, validation, cancellation and progress where emitted, plus streaming and reconnection behavior according to advertised capabilities. Use `subscriptions/listen` for current board-resource updates and the SDK's stateless compatibility mode for legacy request and response calls. |

Use the release coverage matrix to map ordinary Planner workflows to MCP. Site account administration, permanent purge, native install, binary file transfer and migration stay in their authenticated application or operator interfaces. Test both protocol profiles using an SDK client and test Codex and Claude with the profile each actually negotiates. Check malformed requests, version mismatch, auth discovery, origin enforcement, read-only grants and connection revocation. Route protected results with private cache policy and check the grant before each data delivery.

## Risks / Trade-offs

- Community parity can grow silently → Track every upstream workflow against a concrete release case or a documented exclusion. Compare behavior using upstream test instances and independently written fixtures.
- SQL and blob backups can be captured at different times → Take a quiesced matching snapshot, record its manifest and report missing files, bad checksums and orphan relationships before cutover.
- An overly broad role conversion can expose private data → Compare an explicit source/target allow-deny matrix. Make unmapped authorization data a preflight blocker.
- MongoDB data and file storage have separate lifecycles → Coordinate backups with workspace writes paused. Reconcile both copies and test clean-host restore before release.
- Serialized writes limit throughput → Measure board moves, reads and recovery against a representative workspace. Keep slow work outside the commit gate and record capacity from packaged-host tests.
- Dual MCP versions and client OAuth onboarding differ → Test each profile against a real client and the published specification. Keep one domain surface behind both adapters.
- A bundled database adds patch and distribution responsibility → Track the pinned versions and corresponding source, make upgrades repeatable, and verify isolation on a host with a separate MongoDB instance.

## Migration Plan

1. Rehearse on a copy. Record source release, edition, database schema, snapshot identifiers and storage layout. Run preflight, import and reconcile. Review role outcomes and any explicit exclusions.
2. At cutover, pause PLANKA writes, capture a final matched snapshot and prepare a fresh Planner staging import. Keep PLANKA pointed at its original data.
3. Use operator-only read-only verification to check reconciliation, representative accounts and boards, file downloads, and private-board access. Establish at least one usable administrator and save a rollback point and a target backup.
4. With operator approval, activate the staged destination, switch the application URL and resume writes in Planner. Use account reset and MFA enrollment to onboard imported users. Keep the original source and backups for the agreed retention period.
5. Before Planner accepts writes, rollback is a routing change back to PLANKA. After writes begin, capture Planner's data and reconcile those new edits with the operator before switching users back. The two applications have independent databases.
