# Planner accounts, authorization and MCP contract

## Permission matrix

Start every operation with an active account in the active Planner generation. Resolve a child through its current board and project. A board reader is a direct member, a project manager, or a site administrator for a shared project without an owner-manager. A board editor is a direct editor member. A commenter is an editor or a direct viewer with the comment flag. Shared, private and hidden attributes never create anonymous reads. Resolve requested subresources before projecting any sibling resources.

| Action | Required capability |
| --- | --- |
| Create project | Site administrator or project-owner site role. Creator becomes manager. A private project has one owner-manager. |
| List project, read or favorite | Manager or shared-project admin sees all its boards. A board member sees only assigned boards. Hidden state changes workspace presentation independently. |
| Edit project, background or project field templates | Project manager. A shared-project admin may edit hidden state without editing project content. Private owner can convert to shared. Shared-project admin can make private with the sole remaining eligible manager. |
| Add or remove project manager | Shared projects only. Caller is manager or site administrator. Add target is active site admin or project owner. Preserve at least one manager. Delete project requires manager, explicit confirmation and zero boards. |
| Create, edit, reorder or delete board | Project manager. Creation assigns the creator direct editor membership and creates archive and trash. |
| Add, edit or remove board membership | Project manager. Add target is active. Manager without site admin/project-owner rights may add self only. A member can remove self. Viewer comment defaults false. Editor override is null. |
| Read board, cards, activity, attachments or search | Board reader. Resolve the specific card and board before returning names, counts, links or files. |
| Follow board or card | Direct board member acting for self. Card assignment adds an implicit nonpermanent follow. Unassignment removes only the implicit follow. Explicit user follow persists. |
| Edit board content | Direct editor. Validate destination board, label scope, current member assignee, attachment ownership and field-group ownership independently. |
| Move card or finite list across boards | Direct editor on both boards. Move linked checklist tasks only within the owning card and require target readability when linking. |
| Duplicate card | Source project manager or source editor, with direct editor on destination. |
| Sort, bulk archive, and clear trash | Sort finite list and bulk archive closed list as editor. Clear confirmed trash as manager or editor. |
| Comment | Commenter may create, edit own and delete own with current rights. Manager can remove a comment as moderation. |
| Inbox and personal preferences | Current recipient or owner only. Apply current board scope to inbox projections and counts. |
| Account directory and administration | Admin/project owner can use directory lookup for eligible choices. Site admin performs provisioning, disablement, reset and role changes. Ordinary boards expose a minimal current-person projection only. |

On board membership removal, in one command unlink board and card follows, remove card assignments and clear task-assignee fields on that board for the departing member. Compute permissions again. Revoke read, file and live access only when membership was the last read path. Test surviving manager and shared-admin read paths along with manager removal, admin demotion and shared-to-private conversion. Candidates listed for a membership control use that exact scope and eligibility, including self-only managers. Apply the same matrix to web, REST, file previews, conditional requests, range requests, SSE, migration validation and MCP.

## Account lifecycle and web endpoints

| Endpoint under `/api/v1` | Inputs and outcomes |
| --- | --- |
| `POST /session/login`, `POST /session/verify-mfa`, `GET/DELETE /session` | Login accepts identifier and password. Returns either authenticated account, second-factor challenge or enrollment-required status. Verify accepts challenge ID and one TOTP or recovery code. Browser receives an opaque cookie only on successful status. GET returns safe identity and permission projection. DELETE revokes current browser session and its streams. |
| `POST /recovery/consume`, `POST /mfa/enrollment`, `POST /mfa/enrollment/verify` | Consume a one-time installer/admin grant and enter limited setup. Set new password, get enrollment secret once, verify a current code and create recovery codes. Previously protected source accounts complete this before regular login or consent. |
| `GET/PATCH /me/profile`, `PUT/DELETE /me/avatar`, `GET/PATCH /me/preferences`, `POST /me/password` | Update name, nullable username, email, phone, organization, language and safe preferences with current session and reauthentication for identity/password. Use unique normalized identifiers. An admin-verified reset handles imported accounts and changed verified email where needed. Process own avatar with private media checks. |
| `POST /me/mfa/recovery-codes`, `DELETE /me/mfa`, `GET /me/trusted-devices`, `DELETE /me/trusted-devices/:deviceId` | Require reauthentication plus MFA to renew one-time recovery codes or disable MFA. Device listing and deletion are owner-only. Activation records grant trust only after successful MFA. |
| `GET/POST /admin/accounts`, `PATCH /admin/accounts/:id`, `POST /admin/accounts/:id/recovery` | List permitted details, provision roles, disable/reactivate and produce an expiring recovery grant. Audit the administrator and protect the last usable administrator under the shared write gate. |
| `GET /me/connections`, `DELETE /me/connections/:id` | List own OAuth client, when linked, scopes and status. Revoke one grant without affecting another client or browser session. |

Use async scrypt with versioned parameters `N=131072,r=8,p=1`, random 16-byte salt, 32-byte derived key, and a bounded two-job hashing queue. Persist only password verifiers. Enforce 12–128 character passwords and use generic invalid-login errors. Rate-limit by identifier digest and source IP. Use opaque session, challenge, recovery and trusted-device tokens generated from at least 256 bits of randomness, with digests stored server-side. Set a Secure, HttpOnly, SameSite=Lax, path-scoped session cookie. Check exact browser origin and CSRF token for state-changing endpoints after login. Use a five-minute MFA challenge, 30-minute operator grant and 30-day optional trusted device expiration. Use TOTP with six digits, 30-second steps and ±1 step skew. Reject replay and consume recovery codes with atomic compare-and-set. Store TOTP secrets encrypted with an installation key and print recovery codes once. Enforce documented personal inactivity timeout preference with a 30-day absolute session maximum.

Use site roles `admin`, `projectOwner` and `boardUser`. Preferences accept editor modes `wysiwyg` or `markup`, home views `groupedProjects` or `gridProjects`, project orders `byDefault`, `alphabetically` or `byCreationTime`, and auto-logout `never`, `2m`, `5m`, `10m`, `30m` or `12h`. New accounts default to grouped, default order, rich editing and `12h` inactivity. Default own-card follow to false, follows on commenting to true, favorites visibility to true and recently changed highlighting to enabled. Map supported imported preferences directly. Report unsupported display preferences and use the explicit new-account default for that field.

Logout affects the current browser session. Account disablement, credential reset, password change or required MFA reset invalidates existing sessions, trusted devices, recovery state where appropriate and OAuth grants, along with associated streams. Reactivation starts a fresh authentication lifecycle. During staging, allow enrollment alone and deny ordinary REST, SSE, attachment access and consent. Use a local confirmation path for high-impact administrative mutations. Hard deletion of accounts and its project cascades are explicitly deferred. Use disablement and retain imported historical actor links.

## Activity, inbox and live updates

- Separate material-mutation audit, committed live events, activity entries and notifications. Audit actor, client where applicable, operation, scoped resource IDs, command ID and timestamp. Use protected storage and stable event IDs. Exclude secrets, external URLs and borrowed user identifiers from logs. Origin for an audit record is `web`, `mcp`, `operator` or `system`.
- Record activity for card create/move, assign/unassign and task complete/reopen. Keep comments as separate records. Bulk archive writes one move activity per card and sends no individual follower notifications. Cross-board transfer sends a removal-only event to the old board and detail only to authorized destination recipients.
- Single same-board card move notifies the authorized union of board and card followers excluding actor. Assignment notifies the newly assigned eligible user except self. New comments add authorized board-member mentions to the follower union with one notification per recipient and mention priority. Edits and ordinary events do not produce extra notifications. Verify disabled and revoked users receive nothing new. Keep all eligible imported read/unread history and paginate it. Quarantined rows cannot contribute to badge counts.
- Board snapshot and event timing use the platform replay contract. A per-recipient event projection can omit case titles and target IDs across an authorization boundary. Send heartbeats, authorize each replay and flush, and remove buffered data on revocation. Test races between read/subscribe, repeated event delivery, reconnect, removal and destination transfer.
- Authorize every file lookup before issuing bytes, status, length or cache metadata. Protect attachments by card/board, backgrounds by project, and avatars by allowed user projection. Use private non-storable protected responses with safe download names. A shared digest grants no access through a separate attachment. Test byte parity, disallowed HEAD/range and removed cover.

## MCP operations and transport

Use the REST operation IDs in the workspace contract as the source for tool declarations. `projects`, `boards`, `lists`, `cards`, `labels`, `checklists`, `tasks`, `fields`, `comments`, `attachments`, and `notifications` use the corresponding singular tool prefix. `activity` stays unchanged. Convert each camel-case action to snake case. Examples are `boards.get → board_get`, `cards.move → card_move`, `cards.duplicate → card_duplicate`, `lists.archiveCards → list_archive_cards`, `fields.setValue → field_set_value`, `comments.create → comment_create` and `notifications.readAll → notification_read_all`.

Expose every ordinary workspace operation in that registry with these exceptions. Board SSE is a browser endpoint with separate MCP subscriptions. Raw uploads/downloads and attachment thumbnail bytes use browser file endpoints. Provide authenticated browser URLs and metadata in tools. Permanent project and board delete, card purge, trash clear, binary background upload, site accounts, login and credentials, personal security, install, migration, backup and recovery stay in their UI/operator routes. Board settings, field templates, membership and reversible changes remain available through their normal role checks. For each enabled tool, assert same DTO, revisions, normalized error, persistence, activity and audit as its REST twin. Omit inaccessible items and mutation effects and avoid exposing private names through error metadata.

- Use `planner:read` for reads and require `planner:read` plus `planner:write` for mutations. Consent is explicit and shows account, client, scopes and redirect host. Keep discovery's initial required scope to read. Return a standards-compliant 403 insufficient-scope challenge when a known operation exceeds a grant. Resource-level denial uses the same visibility outcome as REST.
- Register readable `planner://boards/{id}` and `planner://cards/{id}` resources and permission-checked `board_status` and `board_triage` prompts. Tool results are typed and bounded with pagination. Do not rely on resources or prompts for the named clients' common read/write workflows. Modern board-resource notifications are available only to currently authorized grants.
- Mount the pinned official SDK with one Fastify `/mcp` path at the canonical HTTPS origin. Current 2026-07-28 validation uses `server/discover`, required per-request metadata and protocol/method/name headers matching body. Use request-scoped `subscriptions/listen` streams. Legacy 2025-11-25 compatibility uses initialize, initialized and negotiated version in stateless Streamable HTTP. Return SDK-compliant 405 for unsupported GET/DELETE session operations and advertise no legacy resource subscription. Check named clients' actual negotiated versions and account flows before freezing the compatibility matrix.
- Serve protected-resource metadata and issuer discovery. Use issuer-bound, resource-bound S256 authorization codes with a five-minute expiry and one-time consumption. Use 15-minute opaque access and rotating refresh with a 30-day maximum grant lifetime. Store hashed or provider-safe credential state in the isolated MongoDB adapter, with atomic artifact redemption and grant-family revocation on replay. Refresh requests are form-encoded. Publish `offline_access` support. Verify client, scope, resource, account and grant status on each call and stream delivery.
- Pin the provider's experimental CIMD support and advertise `none` for public-client exchange. Use restricted fetching for verified Codex and Claude client documents and allow an operator-pre-registered client. Validate exact hosted redirects and exact loopback host/path with the allowed port exception. Preserve RFC 9207 issuer checks. Disable unrestricted client registration and metadata fetching. Protect ID-bound metadata from DNS changes, redirects to local targets and misleading claims.

## Release acceptance

Run independent real-client checks for Codex CLI, Codex desktop, Claude Code and a Claude custom connector. Use a synthetic workspace and a public HTTPS port 443 endpoint only where the hosted Claude client needs it. Verify add/login, consent, discovery, permitted read/write, denied read-only edit, actor/client audit and revoked call on each surface. Capture actual client build or hosted date and negotiated profile. Include Codex issuer-bound ephemeral `127.0.0.1`, desktop fresh Authenticate, Claude Code `localhost` and `127.0.0.1` and hosted `https://claude.ai/api/mcp/auth_callback`. Run protocol tests for each published profile independently of the real client matrix. Verify refresh rotation, wrong audience, expired token, invalid origin, malformed method, unsafe redirect and attempted use after loss of membership.
