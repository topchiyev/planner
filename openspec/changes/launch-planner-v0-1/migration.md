# PLANKA migration contract

## Source baseline and inputs

Support Community 2.3.0 and 2.3.1. Require an explicit release and edition declaration plus the tagged structural fingerprint. These patch releases share a schema. Use the actual 23-entry migration ledger through `20260918000000_add_show_card_counter_to_boards.js` and the 34 public tables as the baseline. Record the supported columns, types, nullability and uniqueness in a synthetic schema fixture and assert both tags match. Reject missing or unknown domain columns, unknown migration names, incompatible indexes or schema ambiguity. Database version and release tags are independently reported.

The private 2.3.1 dump contains 34 table sections and 2,152 rows. Before adding the lab account, it had 10 accounts, 4 projects, 3 boards, 250 cards and 51 attachment records. Its manifest verifies 114 file objects, including 48 attachment originals and 66 derivatives. Three referenced original directories are absent. Read-only inspection also found 59 cards whose previous list was deleted, 42 move notifications with missing target relations, and 250 action snapshots referring to a former list. The source schema declares no foreign keys. These are source conditions to classify explicitly rather than infer from row counts.

Input is a quiesced PLANKA database backup restored by the operator to a temporary PostgreSQL instance and a matching copied file tree or versioned read-only object snapshot. Support operator-prepared PostgreSQL custom dumps and the standard documented PLANKA restore path. Planner's archive preparation command can verify and extract a manifest bundle without executing SQL. Allowlist files to extract and reject absolute paths, traversal, links, device entries, duplicate names, and over-limit decompression. Skip deployment env, PostgreSQL globals and certificates. The production source and original backup stay available to the operator. [Tagged PLANKA migrations](https://github.com/plankanban/planka/tree/v2.3.1/server/db/migrations) · [Tagged backup example](https://github.com/plankanban/planka/blob/v2.3.1/docker-backup.sh)

Use manifest fields `formatVersion`, `source.release`, `source.edition`, `source.instanceId`, `source.postgresVersion`, `source.dumpSha256`, `capturedAt`, `asset.kind`, `asset.snapshotId`, and `asset.manifestSha256`. Use stable `source.instanceId` for repeated rehearsals of the same workspace. Logical snapshot fingerprint includes canonical manifest, allowlisted logical projections and asset digests. Omit machine paths, credentials and operator comments from that fingerprint. Source connection settings come from a protected PostgreSQL service file and a dedicated SELECT role. Use `REPEATABLE READ READ ONLY`, UTC session interpretation and allowlisted SQL with keyset pagination. Reject an asset manifest or database fingerprint change on resume.

## Table and field mapping

For imported records retain IDs and nullable `created_at` and `updated_at` in the respective target or restricted provenance. Reserve IDs first, write base rows next, then write edges, deferred references and projections. Map distinct source IDs even when content is identical. Resolve IDs only when the target entity type matches. Source bigint IDs are decimal strings, including JSON snapshot IDs. Generate target UUIDv5 from stable source instance UUID and `entity:sourceId`. Scope the mapping to target generation. Text upload IDs may be decimal strings or UUIDs. Sort numeric source ties numerically before assigning Planner ranks. Map source timestamp without time zone as UTC, retaining six-digit source precision in provenance when the MongoDB date loses precision. Preserve null separately from false, zero or absent values.

### File keys and reconciliation

| Kind | Source key relative to the data snapshot |
| --- | --- |
| File original | `private/attachments/{uploadedFileId}/{filename}`, using the exact stored leaf bytes. |
| File derivatives | `private/attachments/{uploadedFileId}/thumbnails/outside-{360,720}.{thumbnailsExtension}`. Verify present derivatives or regenerate supported variants from the verified original. |
| User avatar | `protected/user-avatars/{uploadedFileId}/original.{extension}` and `cover-180.{extension}`. |
| Project background | `protected/background-images/{uploadedFileId}/original.{extension}` and `outside-360.{extension}`. |

Use identical keys for materialized and object-backed reads. Match the exact stored leaf name and refuse links, unsafe paths and ambiguous Unicode or case collisions. The source sanitizes names at upload time, so avoid re-sanitizing a stored key on import. Do not derive a key from the display name or fetch link attachments. Stream SHA-256 and length against the independent asset manifest. Source avatar and background metadata can describe the incoming upload before recompression, so compare stored byte count to the manifest. Stage a temporary blob, verify, fsync, rename within one filesystem and record an idempotent target reference. Preserve shared references independently from physical deduplication. Reconcile counts and verify sample downloads through the app. [Tagged asset paths](https://github.com/plankanban/planka/blob/v2.3.1/server/config/custom.js) · [Tagged filename normalization](https://github.com/plankanban/planka/blob/v2.3.1/server/utils/filenamify.js)

### Deterministic exception policy

- Unknown roles, missing active parent/ACL edges, duplicate user identities, malformed canonical values, wrong hashes, and ambiguous or unsafe paths are hard blockers. Record an opaque legacy ID, entity type and reason code in the local operator report. No public raw data mapping file.
- For a missing prior list, retain its source ID as restricted provenance. Preserve the card and archived/trash state. An editor must choose an eligible restore destination. For a historical action referencing a missing target, retain the typed snapshot and do not manufacture a live link. Quarantine orphan inbox delivery rows with unsafe or unavailable targets and preserve their original read state in the reconciliation ledger. Do not show them or count them as unread. Count each preserved raw record in input reconciliation.
- Missing original assets block cutover by default. Stage those records as unavailable so verification can produce an exact approval list. An operator approval file contains `{runId,snapshotSha256,missing:[{type,sourceId,reason}]}`. Validate that its unique entries exactly cover the absent originals and no other cases. This yields a visible unavailable-file record, preserves the cover/attachment association where applicable, and never fabricates bytes. A corrupt or mismatched asset remains blocking. Record approved IDs and residual missing counts at activation. The private reference rehearsal is expected to block under the default policy.
- In read-only rehearsal and import, never deliver mail, webhooks, notifications, or other integration traffic. Preserve eligible historical inbox entries only. Validate every event or media projection through the active access policy.

## Operator workflow and states

| Command | Required behavior |
| --- | --- |
| `plannerctl migration prepare --archive FILE --work-dir DIR` | Verify archive layout and manifest. Extract allowlisted backup inputs and print safe paths for the operator's isolated PostgreSQL restore. Keep original untouched. |
| `plannerctl migration preflight --manifest FILE --source-service NAME --assets-root DIR` or `--asset-service NAME` in place of `--assets-root` | Validate stable source and protected access, target prerequisites, schema, asset keys, file availability, estimate and eligibility. A protected object-service file supplies immutable snapshot reader settings. Use exactly one declared local/object asset reader. Print run ID, manifest hash and fault categories. |
| `plannerctl migration stage --run ID`, `resume --run ID`, `status --run ID` | Write inactive generation in bounded batches. Record table, last source key and fingerprint only after durable effects. Replay deterministic upserts. Keep readers on the old generation or in setup mode. On mismatch leave staged evidence and require a new run. |
| `plannerctl migration verify --run ID`, `report --run ID --format json` | Reconcile source counts against normal, quarantined, excluded and approved-unavailable states. Check ID maps, ranks, permission matrix, blob digests, logical counts and representative authorized read paths. Print structured reasons with no original values or credentials. |
| `plannerctl migration bootstrap-admin --run ID --source-user ID` | Create one privileged, expiring setup grant for a named enabled imported admin. Verify recipient out of band. Enroll the required factor before access. If no eligible admin exists, require explicit local creation of a new admin and audit it. Preserve all imported roles. |
| `plannerctl migration activate --run ID --expect-manifest SHA256 [--approve-missing-assets FILE]` | Require successful verification, usable admin, confirmed prior backup and exact approved fingerprint. Persist the canonical approval digest with the run and match it in the activation CAS. Use one CAS to enter `activeReadOnly`. Prove login and sample board/media access with workspace writes still frozen. |
| `plannerctl migration enable-writes --run ID`, `plannerctl migration rollback --expect-generation ID` | Explicitly enter `writable`. Establish the durable rollback fence under the writer gate before applying the first workspace effect. Before the fence restore prior generation/routing under a matching CAS. After the fence refuse automatic rollback and require a recovery export, prior backup and operator reconciliation of new edits. |

State flow is `preflighted → staging → verifying → verified → activeReadOnly → writable`. A verified run can carry absent-file approval requirements. Activation remains blocked until its approval file is validated. Any hard-blocked or failed stage stays unavailable. Resume only the same fingerprint when the error is recoverable. Each state change is auditable and idempotent on retry, including a crash after a successful activation CAS before response. Recovery replay and maintenance use the platform writer lock. Before routing cutover freeze the source, finalize a consistent capture, rehearse and verify, collect a target backup and preserve source rollback.

Read-only activation allows necessary browser authentication, session records and operator audit. It blocks workspace writes, inbox read-state changes and new OAuth grants until `enable-writes`. For the first authorized workspace command, write a durable installation fence with its command ID before executing any effect. Recovery rechecks the fence before replaying a prepared command. Rollback uses the same writer gate and rejects a prepared or committed workspace mutation even if the HTTP response was lost. A crash after the fence but before effects requires explicit reconciliation as the conservative case. Test activation retry with the approved exception digest and both sides of the first-write fence.

## Fixtures and acceptance

- Commit independently generated PostgreSQL schema/data and asset fixtures. Give both declared releases one test. Include physical paths for matching, unavailable and corrupted originals, case and normalization edge cases, duplicate assets, valid and unsafe link URLs, and avatar/background encoded-size differences.
- Include adjacent integers above JavaScript's safe integer, tied ranks and UTC microseconds, roles and null usernames, disabled and MFA accounts, stale prior list, orphan inbox and historical action snapshots, shared upload references, template instance triples and cross-board task permissions.
- Fault injection interrupts file rename, MongoDB write before checkpoint, reconciliation before verification, activation pointer before reply, and cutover before first write. Assert stable IDs, no duplicate rows, source read-only behavior, and original snapshot integrity.
- Use private reference metadata only as additional rehearsal evidence. Record baseline table/file counts, default blocking result for the three absent originals, and explicit outcome for stale historical relationships. Hosted-client tests and repository fixtures use synthetic data.
